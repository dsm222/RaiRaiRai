# 阅读顺序与改动解释

## 阅读顺序

按“后面的逻辑依赖前面的逻辑”排列：

1. 类型、常量、数据结构和公共接口。
2. 被调用的底层实现。
3. 业务主流程。
4. 入口、界面和外围适配。
5. 测试与配置。

同一实现的 `.h` 与 `.cpp` 必须相邻，`.h` 在前；判断依赖时移动整个文件组。跨目录配对要依据真实包含关系、类型和实现，不只依赖同名。

## 字段写法

- `title`：用一句中文定位本段职责，不写“修改代码”或“逻辑优化”。
- `originalLogic`：说明原来的触发条件、关键判断、数据流、状态变化和结果。新增代码要说明原流程在哪里结束以及此前缺少什么能力。
- `modifiedLogic`：说明实际新增、删除或改变的分支，数据如何流动、调用谁以及结果如何变化。
- `requirementRelation`：先引用最具体的需求编号，再说明需求要求什么、本段哪个行为完成它、用户能观察到什么。

## 质量要求

- 用中文完整句子，先说明本段在整体流程中的位置，再解释条件和数据流，最后落到可观察结果。
- 解释业务行为后再补必要的类名和函数名，不逐行翻译代码，不堆术语。
- 各改动块独立说明，不写“同上”，不批量套用高度相似的固定句式。
- 只描述真实 diff 中存在的行为，不编造保护、测试或效果。
- 写需求关系前重新核对需求原文。若代码无法对应已有需求，先判断它是否为不必要改动，不临时创造需求。
- 不写风险评估，也不要在 JSON 中添加 `risks` 字段。
